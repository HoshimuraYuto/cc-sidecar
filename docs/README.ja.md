# cc-sidecar

[English](../README.md)

[Claude Code](https://docs.anthropic.com/en/docs/claude-code) が Bash から別エージェントの CLI（`codex exec`、`claude -p`、`gemini -p`）に処理を委託する際、その実行状況を監視するプラグインです。プラグインがない場合、委託した処理は完了するまで何も表示されないただのシェルコマンドとして実行されるため、進捗状況がわかりません。このプラグインを導入すると、委託した処理が **エージェント実行（agent run）** として管理され、相手のエージェントが現在何をしているか、これまでに何を行ったか、どのセッションを再開できるかを一目で確認できるようになります。なお、Claude Code のコンテキストには最終的な回答のみが送られます。

```
◆ Codex     ⠹ 0:23 · 4 steps · gpt-6-astra
  › $ rg --files -g '*.go' | wc -l
✦ Gemini    ✓ 0:41 · 6 steps · gemini-3.8-flash
  » 30 files.
```

## インストール

マーケットプレイスを一度登録し、そこからプラグインをインストールします。

```
/plugin marketplace add HoshimuraYuto/cc-sidecar
/plugin install cc-sidecar@cc-sidecar
```

ファンクションフック（`function hooks`）は早期アクセス機能のため、Claude Code はこの機能を有効にするフラグを付けて起動します。

```sh
CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude
```

このプラグインには実行時の依存関係はありません。監視対象の CLI（`codex`、`claude`、`gemini`）が `PATH` に通っている必要があります。

## 設定

`mode` オプションは、`/config` またはプロンプトから直接指定できます。

```
/cc-sidecar          open the pane, print the mode and resumable sessions
/cc-sidecar hint     switch the mode (persisted through /config)
```

| Mode             | 動作                                                                          |
| ---------------- | ----------------------------------------------------------------------------- |
| `pane` (default) | エージェントの CLI が起動すると同時にペインが開き、表示されたままになります。 |
| `hint`           | ペインは開かず、プロンプトのヒント行に実行状況が表示されます。                |
| `both`           | サイドペインとヒント行の両方に表示します。                                    |
| `off`            | 実行状況は追跡されますが、自動的に画面が開くことはありません。                |

この設定は、`settings.json` の `pluginConfigs` 内に保存されます。プラグイン ID は、マーケットプレイスからインストールした場合は `cc-sidecar@cc-sidecar`、チェックアウトしたディレクトリを `--plugin-dir` で読み込んでいる場合は `cc-sidecar@inline` がキーとして使用されます。

```json
{
  "pluginConfigs": {
    "cc-sidecar@cc-sidecar": { "options": { "mode": "both" } }
  }
}
```

`/cc-sidecar` コマンドを使用すると、`off` を含むすべてのモードでペインが開くため、コマンドひとつでいつでも履歴を確認できます。古いバージョンの Claude Code を使用している場合や設定行がロックされている場合など、設定の変更が拒否されたときは、プラグイン独自のローカルストアに設定を保存してユーザーに通知します。

ペインを手動で閉じた場合は、たとえ `pane` モードであっても、そのセッション中は閉じた状態が維持されます。再び表示したいときは、いつでも `/cc-sidecar` コマンドで再表示できます。これにより、一度閉じたペインが何度も勝手に開いてしまうのを防ぎます。

## なぜ必要か

Claude Code から他のエージェントを実行する方法は3つあります。

| Route | Tools the other agent uses    | What you see while it runs                                                             |
| ----- | ----------------------------- | -------------------------------------------------------------------------------------- |
| proxy | **Claude Code's tools**       | 実行ループを Claude Code が管理するため、進行状況が画面にリアルタイムで表示されます。  |
| MCP   | its own, behind one tool call | 実行が完了して単一のツール実行結果が返るまで、画面には何も表示されません。             |
| CLI   | **its own native tools**      | 実行中は何も表示されず、完了した時点で Bash の実行結果（標準出力）のみが表示されます。 |

CLI を経由するルートでは、呼び出されたエージェントがネイティブツールを直接使用できる一方で、実行中の進捗が全く見えなくなってしまいます。さらに、コマンドの終了時には CLI が標準出力（`stdout`）に書き出したすべての内容が Claude Code のコンテキストにそのまま取り込まれてしまいます（`codex` の場合は、実行内容のログ全体が該当します）。このプラグインは、前者の進捗を可視化し、後者のコンテキスト肥大化を防ぐことで、これら2つの課題を解決します。CLI の呼び出しは処理が完了するまで同期的にブロックされ、途中で介入することはできないため、このプラグインは1回限りの委託（ワンショットデリゲーション）を前提に設計されています。

## Pane

プラグインのインターフェースは、一覧画面と実行履歴画面の2つで構成されています。

### 一覧

ステータス記号、エージェント、状態、経過時間、ステップ数、モデルが表示され、その後にエージェントが現在行っているアクションが続きます。2行目はイベントの種類に応じて色分けされており、メッセージは `»`、推論（薄色）は `·`、ツール呼び出し（シアン）は `›` で表されます。この行は最大2行まで折り返して表示され、それを超えると `…` で省略されますが、履歴画面から全文を確認できます。完了した実行には `✓` または `✕` が表示され、10秒間表示された後に自動的に消去されます。

### 履歴

ペインにフォーカスがあるときにエージェントの番号キーを押すか、エージェント名をクリックして選択すると、その実行の全ステップを古い順に表示できます。連続する重複出力は折りたたまれ、最大で直近の40ステップまで確認できます。ヘッダーには実行状態とモデルが表示され、その後に実際に実行されたコマンドと、その CLI を再開するためのコマンドが続きます。

履歴の表示中は実行データが期限切れになることはなく、`← back` をクリックするかホットキーの `b` を押すと、その時点から10秒の消去タイマーがリセットされます。これにより、履歴を読んでいる最中に実行データが消えてしまうのを防ぐことができます。

## ヒント行

`hint` モードおよび `both` モードでは、実行中のプロセスがプロンプトフッターの下にある `PromptHint` 行に表示されます。

```
⏵⏵ auto mode on (shift+tab to cycle) · ← for agents
✳ Claude ⠹ 0:18 · 1 step · claude-haiku-4-5 › $ sleep 20
```

この行にはエージェント、状態、経過時間、ステップ数、モデルが表示され、その後にエージェントの現在のアクティビティが続きます。複数の実行がアクティブな場合は、ペインと同じ順序（古い順）で、それぞれの実行に専用の行が割り当てられます。エンジン本来の描画（`next(e)`）は最後の行の中に含めています。これを含めないツリーはモードラベルの右側に配置され、2行目がラベルの幅の位置から始まってしまうためです。

サブエージェントの一覧（`● main` / `◯ general-purpose ...`）は `PromptHint` 領域の下に表示されます。この一覧はカスタム描画の対象外であるため、起動された順序に関わらず、CLI による実行は常にサブエージェントの一覧よりも上に表示されます。

このプラグインでは、`$.ui.status`（ステータス行の上に警告記号とプラグイン名付きで描画される）、`ToolProgress`（すべての実行中プロセスで共有され、最後のプロセスの下に表示される単一のインジケーター）、`ToolUse`（Bash 呼び出しが `Running 1 shell command` グループに折りたたまれると、専用の行が表示されなくなるため）のいずれも使用していません。

## 再開

CLI の呼び出し自体は1ターンで終了しますが、セッション ID が JSONL ログに保存されているため、一覧から行が消えた後でも実行を再開できます。`/cc-sidecar` コマンドを実行すると、直近5件の実行履歴が表示されます。

| CLI    | Resume                   | Where the id comes from                                                                                   |
| ------ | ------------------------ | --------------------------------------------------------------------------------------------------------- |
| codex  | `codex exec resume <id>` | `thread_id`                                                                                               |
| claude | `claude --resume <id>`   | `session_id`                                                                                              |
| gemini | `gemini --resume latest` | `init.session_id`（ID による再開はサポートされておらず、`latest` またはインデックス番号のみ指定可能です） |

## 検出

このプラグインは、コマンド名を照合することで `codex`、`gemini`、`claude` を検出します。`hooks/hooks.tsx` 内の `AGENTS` に別の CLI を追加した場合、検出と経過時間の追跡は行われますが、詳細な実行内容の解析に対応しているのは、これら3つの主要エージェントのみです。

`cd x && FOO=1 codex exec ...` のようなコマンドも正常に検出されます。これは、コマンドの各セグメントを走査する際、環境変数の割り当て部分をスキップした後に最初の実行可能トークンを探し、そのベース名（ファイル名）で照合を行うためです。

`codex` では、`codex` と `exec` の間に記述されるグローバルフラグ（`codex --search -m gpt-6-astra exec ...` など）を挟む形式にも対応しています。

コマンドセグメントの **最初のトークン** のみが解析対象となるため、別のコマンドでラップした呼び出し（例：`timeout 240 codex exec ...`）をすると検出されなくなります。

クォートで囲まれた文字列は、コマンドを分割する前にあらかじめマスク処理されます。これにより、クォート内に改行やセミコロンを含むプロンプトであっても、検出の妨げになることはありません。また、ヒアドキュメント（Heredoc）の本文もスキップされるため、`cat > f <<'EOF' ... codex ... EOF` のようなブロック内の `codex` を誤検出するのを防ぐことができます。

## コマンドの書き換え

`tool.call` フックは、CLI から構造化データを出力させるために、Bash コマンドを自動的に書き換えます。

| CLI    | Added                                   | Condition                                   |
| ------ | --------------------------------------- | ------------------------------------------- |
| codex  | `--json`                                | コマンドが `codex exec` の場合              |
| claude | `--output-format stream-json --verbose` | `-p` または `--print` が指定されている場合  |
| gemini | `--output-format stream-json`           | `-p` または `--prompt` が指定されている場合 |

`claude` や `gemini` は、これらのフラグをコマンドの末尾で受け取る仕様のため、書き換えが行われるのは **最後のコマンドセグメントがそのエージェントで始まっている場合** のみです。たとえば、`claude -p ... ; echo done` のようなコマンドは書き換えられず、そのまま実行されます。

すでに出力フォーマットが指定されているコマンド（`--output-format json` など）や、パイプが含まれているコマンドは、明示された指定を上書きしないよう、書き換えは行われません。書き換えられなかったコマンドであっても、検出と経過時間の追跡は行われますが、ステップごとの詳細なコンテンツ解析は行われません。

書き換えられたコマンドの最終的な構造や、各フラグを付与している理由など、詳細については [docs/internals.md](docs/internals.md#command-rewrite) を参照してください。

## モデルが読むもの

`--json` が有効化されていると、コマンドの標準出力（`stdout`）はすべて JSONL データになります。これをそのままモデルに送信すると、詳細な実行プロセス（推論のステップ、内部で実行されたコマンド、トークン使用量など）がすべてモデルのコンテキストに流れ込んでしまい、サブエージェントに処理を委託して負荷を軽減するという本来の目的が失われてしまいます。

これを防ぐため、`tool.call` フックが `next(e)` の戻り値に割り込んで書き換え、`stdout` ストリーム全体を最終的な回答のみに差し替えます。これにより、モデルは `--json` を使用しなかった場合と全く同じ、クリーンなテキストのみを受け取ることができます。一方、詳細な実行履歴は UI ペインや JSONL ログファイルから確認できます。この解析処理は完全にフックのランタイム内で実行されるため、生の実行ストリームがモデルのコンテキストに混入することはありません。

書き換えられたすべてのコマンドの標準出力（`stdout`）は、成功または失敗に応じた **ダイジェスト** に置換され、生の JSONL データがモデルに届かないよう制御されます。

| Run                                | Digest                                                                                                                                                                                   |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| finished, ok                       | 最終的な回答（取得できない場合は失敗メッセージ）、または JSON 以外の出力行。                                                                                                             |
| finished, failed                   | 失敗メッセージ（codex の `error` / `turn.failed`、claude の `result.is_error`、gemini の `result.status != success` など）、または取得可能な場合は最終回答、あるいは JSON 以外の出力行。 |
| not finished (interrupted, killed) | 失敗メッセージ、または JSON 以外の出力行、あるいはフォールバック用のメッセージである "The run ended before it produced an answer."                                                       |

JSON 以外の行には、クラッシュ時のスタックトレースなど、構造化ストリームの外部で CLI が出力したテキストが含まれ、プラグインはこれを直近の30行分保持します。書き換えが行われなかったコマンド（パイプを使用しているものや、出力フォーマットを明示的に指定しているものなど）は、このプラグインを導入していないときと同様に、一切加工されることなくそのままモデルに返されます。

ログファイルが読み取れない場合は、代わりにツール実行結果の `stdout` を解析します。フォアグラウンドでは、これは `tee` が書き出した内容と同じものです。

書き換えられた実行結果から除外される情報や、その背景となる設計の意図については、[docs/internals.md](docs/internals.md#what-the-model-reads) を参照してください。

## 既知の問題

**Claude Code の Bash サンドボックス。** サンドボックス機能が有効になっていると、シェルから `$HOME` への書き込みができなくなるため、`~/.cache/cc-sidecar/runs` にあるログディレクトリが作成できなくなります。その結果、ペイン上では実行状態が `starting…` のままになり、バックグラウンド呼び出しは実際の回答の代わりに "no answer was extracted" というエラーで失敗します。これを回避するには、サンドボックスを無効にして実行するか、サンドボックスの設定でこのディレクトリへの書き込みを明示的に許可してください。

**強制終了されたバックグラウンドシェル。** 終了ステータスの記録はシェル自身によって行われるため、外部のプロセスから強制終了されたバックグラウンドの実行は、ペイン上では実行中のまま表示が残り続けます。

## 開発

マーケットプレイスからではなく、チェックアウトしたディレクトリからプラグインを動かす場合は、そのディレクトリを Claude Code に渡します。このときのプラグイン ID は `cc-sidecar@inline` です。

```sh
CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude --plugin-dir .
```

それ以外の作業は pnpm 経由で行います。

```sh
pnpm install          # dev dependencies and the lefthook git hooks
pnpm typecheck        # tsc against .claude/types/claude-code.d.ts
pnpm test             # claude plugin test, with the function-hooks flag set
pnpm format           # prettier over the whole tree
claude plugin validate .
```

`.claude/types/claude-code.d.ts` は、Claude Code の `/plugin-types` コマンドによって自動生成される、プラグイン API の型定義ファイルです。このファイルを手動で編集することは避け、Claude Code をアップデートした後に、同コマンドを実行して再生成してください。

テストスイートがテストキットの制限を回避する方法や、テスト中の画面キャプチャを取得する方法については、[docs/internals.md](docs/internals.md#testing) を参照してください。

### コミットとリリース

コミットメッセージは、[Conventional Commits](https://www.conventionalcommits.org/) の仕様に従う必要があります。コミットの実行時に、`lefthook` がコミットメッセージの `commitlint` によるチェックと、ステージングされたファイルに対する `Prettier` でのフォーマットを自動的に行います。

`main` ブランチへのプッシュはすべて、[semantic-release](https://semantic-release.gitbook.io/) をトリガーします。`feat` コミットはマイナーバージョンを、`fix` および `perf` コミットはパッチバージョンを、フッターに `BREAKING CHANGE` を含むコミットはメジャーバージョンを引き上げます。リリースワークフローは、新しいバージョン番号を自動的に `.claude-plugin/plugin.json` に書き込み、`CHANGELOG.md` を更新した上で、これら2つのファイルを `chore(release): x.y.z` というメッセージでコミットし、GitHub のリリースを公開します。なお、npm へのパッケージ公開は行われません。
